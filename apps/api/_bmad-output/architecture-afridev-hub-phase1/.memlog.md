- (direction) User veut une abstraction entre modules — en cours d'élicitation du type exact
- (decision) AD-1 — Paradigme : Modular Monolith avec interfaces de service pour les appels synchrones cross-module, EventEmitter2 (in-process) pour les side-effects. Prevents: couplage direct entre modules sur les effets de bord ; évite CQRS prématuré.
- (decision) AD-2 — Propriété des données : lectures cross-module via Prisma joins (champs publics uniquement) ; mutations d'une entité réservées au module owner. Prevents: N+1 sur les lectures ; mutation non-contrôlée d'entités partagées.
- (decision) AD-3 — Autorisation : RolesGuard + @Roles() pour les règles de rôle simples (ADMIN, MODERATOR) au niveau controller ; vérifications ownership + contexte métier dans le service. Prevents: logique d'autorisation dupliquée ; règles complexes impossibles à exprimer en décorateur seul.
- (decision) AD-4 — PaymentProvider : tous les providers (Wave, Orange Money, Stripe) actifs en Phase 1, enregistrés dans PaymentsModule via PaymentProviderFactory. Le controller passe uniquement dto.provider ; PaymentsService résout le provider via la factory — le controller est agnostique du provider concret. Prevents: logique de routing provider dans le controller ; couplage controller/implémentation.
- (decision) AD-5 — Redis : refresh tokens (whitelist JWT 7j), rate limiting counters, cache recherche full-text. PostgreSQL : toutes entités métier, sessions modération, idempotency keys webhooks paiement. Prevents: révocation impossible des tokens ; inconsistance sur les limites de requêtes.
- (decision) AD-6 — Stockage fichiers : upload direct frontend→R2 via presigned URL. Flow: POST /upload/presign (NestJS génère URL signée + contraintes MIME/taille) → PUT direct R2 → POST /upload/confirm (NestJS lie l'URL à l'entité). Prevents: double transit bande passante sur serveur ; dégradation UX upload sur connexions lentes.
- (decision) AD-7 — Forme des réponses API : enveloppe uniforme via ResponseInterceptor global (succès: {data, meta?}) et AllExceptionsFilter global (erreur: {error: {code, message}}). Codes d'erreur métier typés. Prevents: shapes hétérogènes par module ; parsing défensif côté frontend.
- (decision) AD-8 — Notifications temps réel : NotificationsModule seul consommateur Socket.io. EventEmitter2 → @OnEvent dans NotificationsService → save DB + push Socket.io. Gateway maintient map mémoire userId→socket (Phase 1, mono-instance). Redis adapter prévu Phase 2 sans changement gateway. Prevents: couplage direct autres modules vers Socket.io gateway.
- (decision) AD-9 — Déploiement : Systalink comme plateforme cible Phase 1. Binds: toute la stack doit être déployable sur Systalink (containerization ou process manager selon ce que Systalink supporte). Prevents: services qui nécessitent des primitives cloud spécifiques (Lambda, Cloud Run) ou une infra auto-gérée non compatible avec Systalink. Rule: les dépendances externes (PostgreSQL, Redis, R2) sont provisionnées séparément ; le backend NestJS est déployé en tant qu'unité unique sur Systalink.
- (decision) AD-10 — Graphe de dépendances modules : les modules domaine (forum, projects, jobs, payments, gamification, notifications, moderation, votes, admin, users, auth) ne s'importent PAS entre eux dans NestJS. Seuls PrismaModule, RedisModule, ConfigModule (infrastructure) peuvent être importés par tous. La communication cross-module passe exclusivement par les interfaces de service injectées (AD-1, appels synchrones) ou EventEmitter2 (AD-2, effets de bord). Prevents: dépendances circulaires NestJS causant un crash au démarrage ; couplage implicite détectable seulement à l'exécution. Rule: si un module A a besoin d'une donnée du module B, il appelle l'interface IBService exposée par B — jamais il n'importe BModule directement.
- (decision) AD-11 — Configuration : toutes les variables d'environnement accessibles uniquement via ConfigService injecté (@nestjs/config). AppModule déclare un schéma Joi de validation au démarrage — var manquante = refus de démarrer avec message explicite. Interdiction de lire process.env directement dans un module domaine. Prevents: var manquante découverte à l'exécution en prod ; config implicite non-déclarée.
- (decision) AD-12 — Logging : nestjs-pino (Pino) comme logger global. JSON structuré en prod, pretty-print en dev (pino-pretty). Logger natif NestJS remplacé par PinoLogger via LoggerModule.forRoot(). Prevents: logs non-structurés inexploitables sur Systalink ; hétérogénéité de format entre modules. Rule: pas de console.log dans le code applicatif — uniquement Logger injecté.
